# DEX 間ファンディング・スクリーナー (シャドーモード)

複数の perp DEX のファンディングレートを年率に正規化して比べ、「会場 A でショート / 会場 B でロング」を
同額建てたときに、**手数料とスリッページを引いても黒字になる差があるか**を記録します。
**売買はしません。注文系 API は呼びません。秘密鍵も API キーも使いません。** 公開 API の読み取りだけです。

目的は、資金を入れる前に「公開記事に出ている年率 30% 級のファンディング差が、自分の執行条件で再現するか」を
実測することです。ポイントは評価額ゼロで扱います (ポイント目的の往復売買は手数料が確定コストなので期待値マイナス)。

## 仕組み

```
 会場ごとの poll_interval_sec で
 ┌─────────────┐
 │ hyperliquid │ 1h 建て  metaAndAssetCtxs + l2Book
 │ lighter     │ 8h 建て  funding-rates + orderBookDetails + orderBookOrders
 │ paradex     │ 8h 建て  markets/summary + orderbook
 │ dydx        │ 1h 建て  perpetualMarkets + orderbooks
 │ binance     │ 8h 建て  premiumIndex          ← 参照のみ (売買しない。ペアに入れない)
 └──────┬──────┘
        │  建てが会場ごとに違うので、まず年率に正規化する
        │     funding_apr = rate / interval_hours * 24 * 365
        ▼
 全ての (ショート会場, ロング会場) × 銘柄 × サイズ について
   gross_apr      = funding_apr(ショート側) - funding_apr(ロング側)
   entry_cost_bps = taker(A) + taker(B) + slip(A の買い板) + slip(B の売り板)
   exit_cost_bps  = taker(A) + taker(B) + slip(A の売り板) + slip(B の買い板)
   breakeven_days = (entry + exit) / (gross_apr * 10000 / 365)
   net_apr(hold)  = gross_apr - (entry + exit) / 10000 * 365 / hold
        ▼
 sqlite に記録: ファンディング / スプレッド (バケット集計) / エピソード / 稼働性 / 板不足
```

- **スリッページは向きを区別します。** 入るときショート脚は売り (買い板を食う)、ロング脚は買い (売り板を食う)。
  出るときは逆です。板は `$1,000 / $5,000 / $20,000 / $100,000` を成行で入れた場合の推定平均約定価格から bps にします
- **板が足りないサイズは評価しません。** 「食べられるところまでの平均」を返すとスリッページを小さく見せてしまうので、
  足りない場合は `depth_misses` に回数だけ記録します
- **エピソード**: `net_apr(14d)` が `min_net_apr` 以上だった状態が何秒続いたか。
  一瞬だけ出る大きな差は実際には建てられないので、継続時間を見ないと意味がありません
  (`tbf/arb/opportunity.py` の `EpisodeTracker` と同じ考え方)
- 会場が落ちている間に古い値で見せかけの機会が出ないよう、`max_stale_sec` より古いスナップショットは計算から外します

## ファンディングの建て (ここを間違えると 8 倍ずれる)

**`check` が会場ごとに API 側から建てを確かめます** (レジストリにそう書いてある、では不十分なので)。
食い違ったら `check` は失敗し、`run` も起動しません。

| 会場 | API | 建て | `check` の自動検証 |
|---|---|---|---|
| hyperliquid | `metaAndAssetCtxs` の `funding` | 1h | `fundingHistory` の支払い間隔が 1 時間であること |
| lighter | `/api/v1/funding-rates` の `rate` | 8h | `/api/v1/fundings` (1h) との検算 (下記) を毎回実行 |
| paradex | `/v1/markets/summary` の `funding_rate` | 8h | `funding_interval_minutes` と突き合わせ |
| dydx | `/v4/perpetualMarkets` の `nextFundingRate` | 1h | `historicalFunding` の支払い間隔が 1 時間であること |
| binance | `/fapi/v1/premiumIndex` の `lastFundingRate` | 8h | `/fapi/v1/fundingInfo` の `fundingIntervalHours` (銘柄によって 8h / 4h / 1h がある) |

Lighter だけ 2 つの endpoint で建てが違うので検算しました (`tests/test_funding.py` で fixture に固定してあります):

- `/api/v1/funding-rates` の `rate` = `9.6e-05` (BTC)
- 同時刻の `/api/v1/fundings?resolution=1h` の `rate` = `"0.0012"`、`value` = `0.9232` (mark ≈ 76,500)
- `9.6e-05 / 8 = 1.2e-05` = `0.0012%` = `0.9232 / 76500` → **`funding-rates` は 8 時間建ての分数、`fundings` は 1 時間あたりの％**

正規化が合っているかの実地チェックは「**同時刻の全会場の年率が近い値に揃うか**」です。
揃わない会場があれば、まず `funding_interval_hours` の設定ミスを疑ってください。

## 使い方

```bash
python -m tbf.funding check                # 会場につながるか・記号が存在するか・建てが API と合っているか
python -m tbf.funding backfill --days 90   # 確定済みファンディングの履歴を取り込む (主指標の素)
python -m tbf.funding run                  # 常駐して記録 (板と価格差。Ctrl-C で停止)
python -m tbf.funding report --days 7      # 主指標 + ライブ計測のレポート
```

設定は 2 つに分かれています:

| ファイル | 中身 |
|---|---|
| `funding.toml` | 銘柄・サイズ・保有期間・閾値・ポーリング間隔の既定・鮮度・履歴の遡り日数・レバレッジ・レポートの窓数 |
| `data/venues.toml` | 会場の一次情報 (エンドポイント・**建て**・手数料とその出所・ポーリング間隔・地域制限・ポイント規則) |

会場を増やすときは `data/venues.toml` に `[[venues]]` を足すだけです。`adapter` が既存のものなら Python の変更は不要。
新しい API 形式なら `tbf/funding/venues.py` の `ADAPTERS` にアダプタを 1 つ足します。
`FUNDING_URL_<会場名の大文字>` で `base_url` を上書きできます。

`reference_only = true` の会場 (海外 CEX など) はファンディングの水準を読むだけで、板も取らず、会場ペアにも入りません。

### レート制限

`poll_interval_sec` は会場ごとに設定でき、既定は保守的な 15 秒です (1 ポーリングあたり 3〜4 リクエスト)。
HTTP 429 / 418 を受けた会場は、その会場だけ一時的に間隔が 4 倍に伸びます。BAN されると計測が止まるので、
間隔を詰めるときは会場ごとの公開上限を確認してください。

## 結果の読み方

`report` の各節:

0. **計測期間とカバー率** — ライブのバケットの欠けと、確定ファンディング履歴 (backfill) の被覆
1. **【主指標】確定ファンディングでの保有期間の損益** — 下記
2. **【主指標】ウォークフォワード (1 窓 = 保有期間)** — 下記
3. **保有期間中の会場間価格差の変化** — 下記
4. **分母の確認** — `net_apr` は**片脚の建玉**に対する率。資本基準は 2 会場ぶんの証拠金で割る
5. (ここから下はライブ計測 = 予測レートのスナップショット。参考)
6. **会場ペア別ランキング** — 予測レートの `net_apr(14d)` 降順。`粗 min/max` が符号を跨いでいたら差は安定していません
6b. **入った瞬間の会場間の価格差と取得時刻のずれ (lag)**
7. **保有期間別** — 往復コストは固定なので、短く持つほど不利になります
8. **銘柄別・サイズ別** — サイズを上げると net が落ちます。落ち方が急な会場は板が薄い
9. **稼働性** — エラー率・p50/p95・429 到達
10. **符号反転** — 反転するとショート側が受け取りから支払いに回ります
11. **ライブのウォークフォワード** (参考)
12. **板不足** — そのサイズを板で約定できなかった回数

### 主指標は「実際に確定したファンディング」です (ライブの外挿ではありません)

ライブ計測で取れるのは各会場が**今返している予測レート**です。`net_apr(14d)` は
「このレートが 14 日続いたら」という外挿なので、**7 日のライブ計測では 14 日保有の損益は検証できません**。
予測レートは 1 時間の中でも動くので、エピソードの長さや符号反転の回数にもノイズが乗ります。

各会場に確定済みファンディングの履歴 API があるので、`backfill` で数か月ぶんを埋めます。

```bash
python -m tbf.funding backfill --days 90
```

| 会場 | 履歴 API | 正規化 |
|---|---|---|
| hyperliquid | `fundingHistory` (1 時間刻み, 500 件/回) + `candleSnapshot` で mark | `fundingRate` をそのまま (+ でロングが払う) |
| dydx | `/v4/historicalFunding` (1 時間刻み, 1000 件/回。`price` 付き) | `rate` をそのまま |
| lighter | `/api/v1/fundings?resolution=1h` (750 件/回) | **`rate` は符号を持たず `direction` が符号。`％` なので /100。`value / rate` が mark** |
| paradex | `/v1/funding/data` の累積 `funding_index` を `history_sample_hours` ごとにサンプル + `klines` で mark | インデックスの差 / mark = その区間に動いた分数 |
| binance (参照) | `/fapi/v1/fundingRate` | `fundingRate` をそのまま |

正規化の約束は 1 つだけです: **`rate` = その区間に建玉に対して実際に動いた分数、ロングが払うとき +**。
`hours` で割れば 1 時間あたりになり、`× 24 × 365` で年率になります (ライブ側の `annualize` と同じ式)。

主指標 (1 節) は「ある時点で建てて `rank_hold_days` 日後に解消したとき、
**実際に確定したファンディングの差 − 往復コスト**」を `entry_grid_hours` ごとの全ての建て時点について出した分布です。
中央値・四分位・最悪・黒字率を並べます。1 本だけの平均ではなく分布を見るのは、
「たまたま良い時点」で判断しないためです。

**往復コストだけはライブ計測の実測値を当てています。** 過去の板は取れないので、
「そのときのスリッページ」は分かりません。ここは近似で、レポートにも明記されます。
ライブで測り続ける必要があるのは板 (スリッページ) と会場間の価格差 (basis) だけです。

### 会場間の価格差は net_apr に入っていません

依頼票の実効スプレッドの式は `taker × 2 + slip × 2` の往復コストだけなので、そのとおりに実装しています。
ただし **2 会場の価格そのものがずれている**ぶんは、この式に入っていません。安い会場でショート、
高い会場でロングを建てると、その瞬間に価格差ぶんの含み損を抱えます。

解消時の価格差が建てたときと同じなら相殺されますが、同じである保証はありません。
実測ではこの価格差が**往復コストと同じ桁**になることがあるので、`net_apr` を動かさずに
別の節として記録・報告しています。採否を判断する側は合わせて見てください。

**効くのは「建てたときの水準」より「保有期間中の変化」です。** ファンディングはプレミアム
(現物指数との乖離) から決まるので basis と相関します。3 節で
`(ロング側の騰落) − (ショート側の騰落)` の分布を履歴の mark 価格から出しています。

### 価格と板は別の鮮度で切ります

`max_stale_sec` (既定 180s) はファンディングレート用です。レートなら 3 分古くても困りませんが、
価格差とスリッページは「3 分前の板」と「今の板」を混ぜると**時刻のずれを差として測ってしまいます**
(BTC は 3 分で 10bps 平気で動く)。そこで価格系は `max_price_stale_sec` (既定 30s) で切り、
2 会場の取得時刻の差 (`lag`) をレポートに併記しています。

### 年率の分母

`net_apr` は**片脚の建玉**に対する率です。実際に必要な資金は 2 会場ぶんの証拠金なので、
資本に対する利回りは `leverage` 次第で変わります (`leverage = 1` なら半分)。4 節に両方出しています。
`min_net_apr` の閾値も片脚建玉基準なので、資本基準に直すと USDC をそのまま置いておく利回りに近い水準です。
閾値の意味をどう取るかは親タスク側の判断です (このモジュールは閾値を変えません)。

### エピソードはデータが古いだけでは閉じません

`net_apr` が閾値を割ったのか、片方の会場のデータが古くなって見えなくなったのかを区別します。
後者で閉じると 1 本の機会が複数のエピソードに割れて、最長継続時間が実際より短く出ます。
古いだけのときは `max_stale_sec` のあいだ保留し、`pending_polls` に回数を残します。

### 全期間の平均を見ないこと

全期間を 1 回通した平均は「どのペアが良かったか」を後から知っている前提なので、実運用の見込みにはなりません。
`report` は期間を窓に分け、**前の窓で最良だったペアを次の窓で持った場合 (OOS)** と、
**その窓を後から見た最良ペア (hindsight)** を 1 行ずつ並べます。`効率 = OOS / 後見最良`。

主指標側 (2 節) では 2 つを守っています:

- **1 窓の長さ = 保有期間** (`rank_hold_days`)。窓 1 日で保有 14 日としてコストを按分すると、
  評価している期間と保有期間が一致しません。
- **乗り換えコストを課す**。前の窓と違うペアを選んだ窓だけ往復コスト 1 回ぶんを引きます。
  課さないと、ペアが頻繁に入れ替わるほど OOS が実際より良く見えます。
  後から見た最良も同じ土台 (今持っているペアはコストなし) で選びます。
  そうしないと持ち続けた窓で OOS > 後見最良 になり、効率が 100% を超えてしまいます。

効率が低い、あるいは OOS が黒字の窓が少ない場合、「最良ペアの年率が高かった」ことには意味がありません。
ペアの入れ替えが必要だと分かるのは次の窓に入ってからなので、実際に取れるのは OOS の側です。

後見最良が 0 以下の窓は効率を `n/a` にしています (負の値との比に意味がないため)。
その窓は「どのペアを選んでも赤字だった」ということなので、OOS の値をそのまま読んでください。

## ファンディング上限の張り付き (上限差エッジ)

TRA-41 (INIT) で実測した型を規則として入れています (`tbf/funding/clamp.py`、`report` の 13 節)。

**何が起きるか。** チェーンが止まって各取引所の入出金が閉じると、現物が会場ごとの
別々の閉じたプールになります。会場の index は自分のプールを参照するので釣り上がり、
ファンディングが上限に張り付きます。**そして上限値は会場ごとに違います**
(INIT の実測で Binance ±2.0%/h、Bybit ±2.0%/h、OKX ±1.0%/h、Hyperliquid ±0.5%/h)。

**発火条件 (ここは一度間違えた)。** 最初は「2 会場以上が上限に張り付き、かつ上限値が違う」と
書きました。ところが 48 時間の確定履歴で測り直すと、long Binance / short Hyperliquid は
27 時間のうち **26 時間勝っているのに、両者が同時に張り付いていた時間は 3 時間だけ**でした。
この条件ではエッジが出ている時間の 9 割を見逃します。効いていたのは両者張り付きではなく、
**片側の非対称**です:

> こちらが払う側の脚が自分の上限に張り付いている間、その脚の支払い要求はそれ以上
> 大きくなれない。相手の脚がその上限を越えて払っていれば、差は払う側の都合では詰められない。

`clamp.detect` はこの条件で拾います (repo の符号の約束は「apr はロングが払うとき +」):

| 張り付いている会場 P | P の役割 | 相手の条件 | 差 |
|---|---|---|---|
| 下限 `-cap_P` | **ショート脚** (払う額が上限で止まる) | `apr_L < -cap_P` | `apr_P - apr_L` |
| 上限 `+cap_P` | **ロング脚** (同じ) | `apr_S > +cap_P` | `apr_S - apr_P` |

両方が張り付いている区間だけは完全に決定論的で、そのとき差はちょうど `cap_loose - cap_tight`
になります (`floor_apr`)。ここはどちらの会場も動けません。`both_pinned_polls` でこの区間の
割合を記録しているので、「決定論的だった時間」と「片側だけだった時間」を後から分けられます。

**上限の出どころ。** 上限は会場ごとではなく**銘柄ごと**に違います
(Binance の BTCUSDT は ±0.3%/8h ですが INITUSDT は ±2.0%/1h)。だから `(会場, 銘柄)` で持ち、
強い順に 3 つの出どころを使います:

| 出どころ | 会場 | 取り方 |
|---|---|---|
| `api` | binance / paradex | `fundingInfo.adjustedFundingRateCap` / `markets.max_funding_rate` |
| `config` | — | `venues.toml` の `funding_cap` (一次情報の出典を `funding_cap_source` に書く) |
| `inferred` | hyperliquid / lighter / dydx | 確定履歴で同じ値が `min_clamp_repeats` 区間以上並び、それを超えない |

**上限が分からない会場は「張り付いている」と判定しません。** 推測で発火させると、
単に大きく振れただけの会場を上限張り付きと呼んでしまいます。`check` が不明な組み合わせを
一覧で出すので、一次情報が見つかったら `venues.toml` に書いてください。

**上限は途中で変わります。** INIT では Binance が精算間隔をイベント中に 4h → 1h に変えました。
`run` は `cap_recheck_sec` (既定 1 時間) ごとに上限を取り直し、変化を `caps` テーブルと
ログに残します。`check` は API の値と `venues.toml` が食い違ったら落とします
(建ての検証と同じ方針で、「レジストリにそう書いてある」を信用しません)。

**参照のみの会場も検出対象にします。** 歪みの発端になるのは index が釣り上がっている会場で、
INIT ではそれが参照側の CEX でした。売買できるかは `tradable` で区別して記録するので、
「規則としては検出できていたのに会場の都合で建てられなかった」が後から分かります。

## つながらない会場があったとき

`check` と `run` で厳しさが違います。

| | `check` (設定の点検) | `run` (計測) |
|---|---|---|
| 建ての食い違い (`funding_interval_hours`) | 落とす | 落とす |
| 売買対象の会場が 1 つつながらない | 落とす | **続ける** (残りでペアを作る) |
| 売買対象の会場が 2 つ未満しか生きていない | 落とす | 落とす |
| `reference_only` の会場がつながらない | 警告のみ | 警告のみ |

7 日回す計測を 1 会場の一時的な障害や、参照用 CEX の地域制限で止めたくないためです。
実行中に落ちた会場は `scanner` が `polls` にエラーとして記録し、その会場を除いて計算を続けます。
`report` の 4 節 (稼働性) で、どの会場がどれだけ落ちていたかを確認してください。

## 実際に資金を入れる前に

このフェーズでは資金を入れません。進める場合でも、少なくとも:

- [ ] 手数料を `fee_source` が `doc` の会場について、自分の口座の tier で実測に差し替える
- [ ] 片脚だけ約定した場合の扱い (どちらを先に出すか、失敗時に残る方向リスク) を決める
- [ ] 符号反転と清算の両方に解消ルールを用意する (`liquidation_bps` は `venues.toml` にある)
- [ ] 地域制限 (`region_restricted`) と資金の出入りの経路を確認する
- [ ] ポイントは評価額ゼロで損益を計算する (遡及没収の実例があるため)
- [ ] Lighter の手数料 0 が自分の口座種別でも成り立つか確認する (`fee_source` は Standard 口座の条件)
- [ ] 往復コストは主指標でもライブ実測値を当てている (履歴の板は取れない)。
      判断に使うサイズで、板の実測をもう一度確認する
- [ ] Hyperliquid の `l2Book` は片側 20 本まで。銘柄を増やすならこの会場だけ板不足が出る
