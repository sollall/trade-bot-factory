# マーケットメイクの準備 (シャドーモードの記録とオフライン再生)

取引所の気配 (板) と約定を記録し、その記録の上で「指値をこう出していたらどうなったか」を
試すための土台です。会場は Hyperliquid (無期限先物)、GMO コイン (現物・レバレッジ)、bitbank (現物) の 3 つです (下の「会場」)。**売買はしません。鍵も要りません。** 使うのは公開 API の読み取りだけです。

目的は、指値の出し方 (クォーター) の改善を、毎回 API を叩かずに記録済みのデータの上で繰り返せるようにすることです。

既存の工場 (`tbf/core`・`tbf/worker`・`tbf/backtest`) は「確定足・毎分の cron・目標の持ち高比率」の作りで、
板も置きっぱなしの指値も取消もありません。マーケットメイクには合わないので、そちらには手を入れず、
`tbf/mm/` を別に足しています。Worker には載せません (`scripts/build_worker.py` が `arb` と同じく除外)。

## 使い方

```bash
python -m tbf.mm record --coins INJ,MON,ZRO      # 記録 (Ctrl-C か SIGTERM で停止)。既定の会場は Hyperliquid
python -m tbf.mm record --venue gmo --coins ETH_JPY,SOL --db data/mm_gmo.sqlite --interval 3
python -m tbf.mm record --venue bitbank --coins xrp_jpy,render_jpy --db data/mm_bitbank.sqlite
python -m tbf.mm report [--hours 6]              # 記録した市場の様子
python -m tbf.mm replay --coin INJ               # 基準のクォーターで再生
python -m tbf.mm replay --coin INJ --param half_spread_bps=4 --param skew_bps=6
python -m tbf.mm replay --db data/mm_gmo.sqlite --since +24h --until +48h --by-day --se   # 長い記録を読む (下の「長い記録を読む」)
python -m tbf.mm paper --coins MON,INJ           # 記録しながら、その場で疑似的に約定を付ける (record を兼ねる)
python -m tbf.mm paper-report [--run 3]          # paper の成績 (run ごと、日ごと、時間帯ごと)
python -m tbf.mm replay --run 3                  # paper の run を記録から流し直して突き合わせる
```

記録先は `--db` (既定 `data/mm.sqlite`。`data/` は git に入りません)。`--hours N` は「今から」ではなく
**記録の末尾から** N 時間を遡ります (後から読み返す使い方が主なので)。

| コマンド | 主なオプション (既定) |
|---|---|
| `record` | `--venue` 会場 (hyperliquid)、`--interval` 気配を取る間隔の秒 (2)、`--trades-interval` 約定を取る間隔の秒 (10)、`--depth` 残す段数 (10)、`--budget` 流量制限のうち使う割合 (0.5)、`--minutes` この分数で止める |
| `report` | `--maker-bps` メイカー手数料 (省くと会場の値。Hyperliquid は 1.5)、`--hours` / `--since` / `--until` 数える期間 |
| `paper` | `record` のオプション + `--param k=v`、`--maker-bps` (別名 `--fee-bps`)、`--latency-ms`、`--no-cross-fill` |
| `paper-report` | `--run` (省くと最後の run)、`--hours`、`--horizons` |
| `replay` | `--coin`、`--run` (paper の run と同じ設定・区間で再生)、`--param k=v` (何度でも)、`--maker-bps` (省くと会場の値。Hyperliquid は 1.5)、`--latency-ms` 指値が板に載るまでの遅れ (250)、`--horizons` 逆選択を測る秒数 (5,30,60)、`--no-cross-fill` 約定の仮定 (c) を外す、`--hours` / `--since` / `--until` 期間、`--by-day` / `--by-hours N` / `--jst` 日ごとの表、`--se` 取り分の ±、`--spot-inventory` 現物の在庫制約 (下の「長い記録を読む」) |

## 会場

`record` / `paper` は `--venue` で会場を選びます (既定は `hyperliquid`)。銘柄は会場の表記のまま書きます。
**db は会場ごとに分けます。** 違う会場の db に足そうとすると起動時に止まります。会場を残す前に作った db は
Hyperliquid として読みます。`report` / `replay` / `paper-report` は db から会場を読むので `--venue` は要りません。

| | `hyperliquid` | `gmo` | `bitbank` |
|---|---|---|---|
| 何の市場か | 無期限先物 | 現物 (`BTC` `SOL` ...) とレバレッジ (`BTC_JPY` ...) | 現物 (`xrp_jpy` ...) |
| 建値 | USD | JPY | JPY |
| 気配が 1 回に返す段数 | 片側 20 | 全段 (200 段前後) | 片側 200 |
| 気配の時刻 | 応答にある | **無い** (応答の `responsetime` で代用) | 応答にある |
| 約定が 1 回に返す件数 | 10 | 100 (ただし下記のとおり 2 行で 1 件) | 60 |
| 約定の id | あり (`tid`) | **無い** (中身から作る) | あり (`transaction_id`) |
| 約定の向き | 仕掛けた側 | **大半は分からない** (下記) | 仕掛けた側 (公式に明記) |
| 値段の刻み | 有効 5 桁の規則 | API の `tickSize` | API の `price_digits` |
| 最小の注文 | 10 ドル (未確認) | API の `minOrderSize` | API の `unit_amount` |
| メイカー / テイカー手数料 | +1.5 / 4.5 bps | 銘柄ごとに API の値 | 銘柄ごとに API の値 |
| 売りから入れるか | 入れる | レバレッジ (`*_JPY`) は入れる。現物は入れない | 入れない (現物として扱う) |
| 流量制限の数え方 | 重み (気配 2、約定 20)、上限 1200/分 (未確認) | 回数。上限は公式に記載なし → 仮に 300/分 | 回数。上限は公式に記載なし → 仮に 600/分 |
| リクエストの間隔 | 銘柄ぶんを同時に | 0.25 秒ずつ空ける | 0.1 秒ずつ空ける |

手数料・刻み・最小数量は、記録を始めるときに会場の API から取って db に残します (`instruments`)。`report` / `replay` / `paper` の
メイカー手数料は、**省くとその値** (銘柄ごと。マイナスはリベート) を使い、`--fee-bps` で上書きできます。
2026-11-22 の値: GMO の現物は BTC・ETH が −1 / +5 bps、SOL・DOGE が −3 / +9 bps、レバレッジの BTC_JPY・ETH_JPY・XRP_JPY は 0 / 0、
SOL_JPY は 0 / +3 bps。bitbank は −2 / +12 bps (btc_jpy だけ 0 / +10 bps)。

金額はすべて建値の通貨で出ます。クォーターのパラメータのうち名前が `_usd` で終わるもの (`size_usd` など) は
「建値の通貨での金額」で、JPY 建ての会場では **既定値を 150 倍** します (`size_usd` は 15,000 円、`max_inventory_usd` は 75,000 円)。
為替レートではなく、桁を合わせるだけの倍率です。`--param` で渡した値はそのまま (円として) 使います。

### GMO コインで気をつけること

- **約定の向きが分からない。** 約定履歴は、1 つの約定が「同じ時刻・値段・数量の BUY と SELL の 2 行」で返ることが大半です
  (2026-11-22 の実測で BTC_JPY は全部、ETH_JPY も全部、XRP_JPY は代金の 85%、現物の SOL は 33%)。どちらが仕掛けたかは
  API からは分かりません (公式ドキュメントの `side` の説明は「売買区分」だけ)。対の 2 行は 1 件にまとめ、向きは `U` (不明) として残します。
  対にならない行だけ `BUY` を買い手主導として読みます (件数は少ないですが、直前・直後の気配と突き合わせて矛盾は 0 件でした)。
- 向きの分からない約定は、再生では「値段が届いた側の指値」に当てます (自分の買い値以下で成立したなら買い指値に、売り値以上なら売り指値に)。
  **約定の向きを使うクォーター (`lean` / `vol_lean` の約定の偏り) は、GMO では材料がほとんどありません。**
- **約定の取得がときどき弾かれる。** 毎分 130 回 (5 銘柄・気配 3 秒・約定 10 秒) の設定で、`ERR-5003 Requests are too many` が
  約定の取得だけに出ました (延べ 844 回中 6 回。気配は 2,711 回中 0 回)。リクエストを 0.25 秒ずつ空けても無くなりませんでした。
  弾かれたら 3 秒休みます。次のポーリングで 100 件ぶん遡れるので、たいていは取りこぼしになりません。
- 約定に id が無いので、(向き, 値段, 数量) と同じ時刻の中での通し番号から id を作って重複を落とします。
  応答が 100 行いっぱいのときは、いちばん古い時刻の行を使いません (対の片方だけが残って別の約定に見えるのを避けるため)。
- 気配に時刻が無く、応答の `responsetime` を使っています。約定の時刻と同じ時計かは確かめられていません。
- `--interval 2` (既定) だと 4 銘柄まで、`--interval 3` で 5 銘柄までです (仮の上限 300/分の半分)。

### bitbank で気をつけること

- 主要な銘柄 (xrp_jpy、eth_jpy) は **スプレッドが刻み 1 つ** に張り付いています (記録の 96〜98%)。内側に指値を出せず、
  最良気配の列の後ろに並ぶしかありません。再生は、刻みに丸めた値段が最良気配と同じなら、その値段に並んでいた数量を
  「前の列」として数えます (仮定 (b))。前の列は数十万〜百万円あるので、(b) での約定はほとんど起きません。
- `/{pair}/transactions/{YYYYMMDD}` で 1 日ぶんの全約定が取れます (未使用)。使えば取りこぼしを後から埋められます。
- 流量制限の公式の記述 (取得系 10 回/秒、超えると HTTP 429) は認証つきの API のもので、公開 API の上限は書かれていません。
  20 分・毎分 144 回でエラーは 0 回でした。

### 国内の会場で、再生が甘くなる点・厳しくなる点

甘くなる (実際より良く見える):

- **現物は在庫が無いと売れないが、再生は売らせている。** 在庫 0 から売り指値が約定します。`replay` の出力の末尾に、
  在庫を 0 より下に押し下げた売りの件数と代金を出します。実際には最初に在庫を持って始めることになり、その在庫の値動きを別に負います。
  GMO のレバレッジ (`*_JPY`) は売りから入れるので、この問題はありません。
- **レバレッジの建玉にかかる費用 (GMO のレバレッジ手数料。日をまたぐとかかる) を入れていない。**
- **GMO の向きの分からない約定を、都合のよい側に当てている可能性。** 自分の買い値より下で成立した約定は買い指値に当てますが、
  それが「買い手主導で、売り板が自分の買い値より下にあった」場合、実際には板が動いた後で、自分の指値はもう無かったかもしれません。
- リベートは約定代金に対して必ず受け取れる前提。実際の付与の条件 (キャンペーン、銘柄の変更) は見ていません。

厳しくなる (実際より悪く見える):

- **仮定 (c)。** 国内の小さい銘柄は約定が少なく (bitbank の render_jpy は 1 時間に 6 件)、気配だけが動きます。
  基準のクォーターの約定は bitbank の eth_jpy・xlm_jpy で全部が (c) でした。`--no-cross-fill` と並べて読んでください。
- **列は取消で減らない。** 刻み 1 つのスプレッドでは列の後ろに並ぶしかないのに、前の人の取消を数えないので、(b) がほぼ起きません。

どちらとも言えない:

- **基準のクォーターは刻みの粗い銘柄に合っていない。** 在庫でずらした値段が相手の気配に当たると、指値は出されません
  (ポストオンリーで弾かれる扱い)。bitbank の xrp_jpy で幅を刻み 1 つ未満にすると、買いが約定した後、売り指値は 598 回中 596 回弾かれました。
  刻みの粗い銘柄では、クォーターの側で値段を最良気配に留める必要があります。

## 記録 (`record`)

銘柄ごとに `l2Book` (気配) と `recentTrades` (約定) をポーリングして sqlite に残します。

| テーブル | 中身 |
|---|---|
| `books` | 気配の上位 N 段。`time` は取引所の時刻、`recv` は手元で受け取った時刻 |
| `trades` | 約定。時刻と `tid` が同じものは 1 回だけ残す。`side` は仕掛けた側 (`B` = 買い手主導、`A` = 売り手主導) |
| `gaps` | 約定の取りこぼしの可能性 (下記) |
| `polls` | ポーリングごとの遅延・エラー・新しく残した件数 |
| `coins` | 数量の小数桁 (`szDecimals`。値段の刻みを決めるのに使う)。Hyperliquid だけ |
| `meta` / `instruments` | この db の会場と、銘柄の決まりごと (刻み・最小数量・手数料・建値の通貨・売りから入れるか)。記録を始めるときに会場の API から取る |

古い記録は消しません (再生の入力なので)。目安は 1 銘柄・2 秒間隔・10 段で 1 日 25MB ほどです。

### 約定の取りこぼし

`recentTrades` が返すのは **直近の 10 件だけ** です (2026-11-22 に実物で確認。件数は指定できません)。
大きな成行 1 本が 10 件以上の指値を食うと、それだけで前回との重なりが無くなります。

前回までに見た約定と今回の応答が 1 件も重ならなかったとき、`gaps` に「その間に取りこぼしたかもしれない」と
残します。抜けた件数は分かりません (ちょうど 10 件ぜんぶが新しかっただけ、のこともあります)。
`report` の約定の件数と代金は **下限** です。取りこぼしが多い銘柄は、約定を取る間隔を縮めるか、
配信で記録してください (GMO コインと bitbank は対応済み。下の「配信で記録する」)。

### 流量制限 (未確認の値で計算しています)

ここは Hyperliquid の話です。GMO コインと bitbank は「会場」の節を見てください (単位は重みではなく回数)。

Hyperliquid の info は IP ごとに毎分の重みの上限があります。`tbf/mm/recorder.py` に入れてある値は
**確かめられていません** (公式ドキュメントはこの環境から届かず、記憶にある値です):

| | 重み |
|---|---|
| `l2Book` 1 回 | 2 |
| `recentTrades` 1 回 | 20 |
| 上限 (毎分) | 1200 |

毎分の重み = 銘柄数 × (2 × 60 / 気配の間隔 + 20 × 60 / 約定の間隔)。値が外れていても踏まないように、
既定では上限の半分 (600) までしか使わず、超える設定は起動時に止めます。既定の間隔 (2 秒 / 10 秒) なら
1 銘柄 180 で、3 銘柄までです。銘柄を増やすなら間隔を延ばします (約定の間隔を延ばすと取りこぼしが増え、
気配の間隔を延ばすと再生が粗くなります)。気配は重みが軽いので、気配のほうを細かく取る配分にしています。

429 を受けたら 30 秒は何も投げません。計算に取り直しは入っていません (`tbf/http.py` は 1 回の失敗で最大 4 回投げます)。
同じ IP からバックテストなど他の用途で Hyperliquid を叩くと、その分も同じ上限から引かれます。

公式ドキュメントで値を確かめたら、`WEIGHT_LIMIT_PER_MIN` / `WEIGHTS` を直してコメントの「未確認」を消してください。

## 配信で記録する (`--source ws`)

GMO コインと bitbank は、公開の配信 (WebSocket) でも記録できます。ポーリングより気配が細かく、約定は全件届き、
GMO では約定の向きも分かります。Hyperliquid は未対応です。

```bash
python -m tbf.mm record --venue gmo --source ws --coins BTC_JPY,ETH_JPY,XRP_JPY --db data/mm_gmo_ws.sqlite
python -m tbf.mm record --venue bitbank --source ws --coins xrp_jpy,eth_jpy,sol_jpy --db data/mm_bitbank_ws.sqlite
python -m tbf.mm paper  --venue gmo --source ws --coins ETH_JPY --db data/mm_gmo_paper.sqlite
```

同じテーブルに同じ形で残るので、`report` / `replay` / `paper-report` はそのまま使えます。
**配信の記録とポーリングの記録は同じ db に混ぜられません** (起動時に止まります)。取り方で再生の仮定が 1 つ変わるためです (下記)。

| | GMO コイン | bitbank |
|---|---|---|
| 接続先 | `wss://api.coin.z.com/ws/public/v1` | `wss://stream.bitbank.cc/socket.io/?EIO=4&transport=websocket` (socket.io 4) |
| 気配 | `orderbooks`。配信のたびに板の全体 (片側 30 段)。1 銘柄あたり毎秒 2 通ほど | `depth_whole_{pair}` (全体、片側 200 段、12 秒に 1 回ほど) と `depth_diff_{pair}` (差分、毎秒 3 通ほど)。全体で置き換え、それより新しい差分を当て直す (公式の手順) |
| 約定 | `trades` に `"option":"TAKER_ONLY"` を付ける。**仕掛けた側の 1 通だけが届き、向きが分かる** (公式に明記) | `transactions_{pair}`。`side` は taker 側 (公式に明記) |
| 受け取りの遅れ (実測) | 気配も約定も 90ms 前後 | 気配 90〜100ms、**約定は 0.5〜1.1 秒** (気配より遅れて届く) |
| 決まり (公式) | 購読の命令は同じ IP から 1 秒に 1 回まで。サーバーが 1 分に 1 回 ping し、3 回続けて返事が無いと切る | サーバーが 25 秒ごとに ping。エラーがあると切られる |
| 1 日の大きさの目安 (上位 5 段) | 1 銘柄 45MB ほど | 1 銘柄 65MB ほど |

**GMO の約定の向きについて分かったこと。** ポーリング (REST) の約定履歴で「BUY と SELL の 2 行」が返るのは、約定の両側 (仕掛けた側と
待っていた側) を両方返しているからでした。配信に `TAKER_ONLY` を付けると仕掛けた側だけになります。同じ 25 分を両方で記録して突き合わせると、
約定の件数と代金は 3 銘柄とも完全に一致し (REST の対を 1 件にまとめる読み方が正しい)、配信の向きは直前・直後の気配と 436 件が整合・4 件が逆でした。
なお REST の対では、**時刻順で先の行 (応答の並びでは後の行) が仕掛けた側** でした (89 組すべて)。これは公式に書かれていない実測なので、
REST の読み方には使っていません (ポーリングの記録では今までどおり向き不明の `U`)。

### 残し方

- **気配は、上位の段 (既定 5 段) の中身が前に残したものから変わったときだけ残します。** 配信は毎秒 2〜3 通来ますが、深い段だけの変化は残しません
  (実測で受け取った気配の 86〜89% を残しました)。同じ時刻 (ms) の気配が続いたら最初の 1 つだけ残します。
  もっと減らすなら `--book-ms 500` (残す間隔の下限) か `--depth 3`。増やすなら `--depth 10`。
- **約定は全件残します。** bitbank は約定の id、GMO は id が無いので中身と通し番号で重複を落とします。
- **切れたら自動でつなぎ直します** (待ち時間を 1 秒から倍々に、最大 60 秒)。90 秒何も届かないときも切れたとみなします。
  切れていた間の約定は取れないので、つなぎ直したときに `gaps` に残します。`polls` には接続と切断を `kind = 'ws'` で残します。
- 取引所の時刻 (`time`) と手元で受け取った時刻 (`recv`) の両方が残ります。`report` は「配信の遅れ」としてその差を出します (時計のずれを含みます)。
- 銘柄の決まりごと (刻み・最小数量・手数料) は、起動時に 1 回だけ REST で取ります。

### WebSocket のクライアント

`tbf/mm/ws.py` に、標準ライブラリだけで書いた小さなクライアントがあります (依存は足していません)。RFC 6455 のうち要る分だけです:
握手、テキストの送受信、送信のマスク、分割フレームの組み立て、ping への pong、close。圧縮やサブプロトコルは扱いません。
`HTTPS_PROXY` があればプロキシ越し (CONNECT) で、無ければ直結でつなぎます。TLS の検証は切りません。

### 再生の仮定で、配信の記録だけ変わるもの

- **列 (b) を気配でも減らします。** 自分の値段に見えている数量が、自分より前の列より少なくなったら、列をその数量まで減らします。
  自分の指値は記録の板に載っていないので、見えている数量はすべて他人のもので、自分より後に並んだ分も含みます。だから前の列はそれより多くはありません
  (前の人の取消が分かる)。気配が細かいのでこの上限が効きます。その値段が残した段数の外に出て見えないときは減らしません。
  `replay` の出力に「※ 配信の記録: ...」と出ます。
- **向きの分からない約定がありません。** GMO も仕掛けた側どおりに当てます (「値段が届いた側に当てる」はポーリングの記録のためだけに残っています)。
- 仮定 (a)(c)、板に載るまでの遅れ、ポストオンリーなどは同じです。**ポーリングの記録の再生結果は変わりません。**
- 気配が細かいぶん、クォーターは毎秒 2〜3 回呼ばれ、値段が変われば出し直します (25 分で 900〜4,900 回)。実際の発注の流量制限は見ていません。

paper を配信で動かすときは、気配を受け取ってから 2 秒待って確定します (気配より前の時刻の約定が遅れて届くため。bitbank の約定は 1 秒ほど遅れます)。
それより遅れた約定は「遅れた約定」に数えます。

### 配信とポーリングで、再生がどれだけ違ったか (2026-11-23、同じ 25 分を両方で記録)

基準のクォーター (幅 3 bps、片側 15,000 円)。「5 秒後」は約定 5 秒後のミッドで測った取り分 (bps、手数料を引く前)。

| 銘柄 | 取り方 | 約定 (a)/(b)/(c) | 5 秒後 | (c) なしの約定 | (c) なしの 5 秒後 |
|---|---|---|---|---|---|
| GMO BTC_JPY | 配信 | 8/0/0 | +0.79 | 8/0/0 | +0.79 |
| | ポーリング | 15/0/2 | −0.48 | 17/0/0 | −0.27 |
| GMO ETH_JPY | 配信 | 26/1/1 | −0.05 | 28/1/0 | +0.02 |
| | ポーリング | 25/0/2 | −0.97 | 25/0/0 | −0.70 |
| GMO XRP_JPY | 配信 | 16/2/8 | −0.21 | 16/0/0 | −0.58 |
| | ポーリング | 19/0/15 | −2.20 | 24/0/0 | −1.99 |
| bitbank xrp_jpy | 配信 | 3/0/7 | −4.23 | 5/0/0 | −4.30 |
| | ポーリング | 6/2/23 | −2.51 | 11/1/0 | −4.84 |
| bitbank eth_jpy | 配信 | 2/0/1 | −4.79 | 2/0/0 | −5.62 |
| | ポーリング | 2/0/19 | −2.58 | 3/0/0 | −9.43 |
| bitbank sol_jpy | 配信 | 0/0/12 | −0.43 | 0/0/0 | - |
| | ポーリング | 1/0/51 | −1.21 | 1/0/0 | +0.17 |

- **仮定 (c) に頼る約定は減りました** (bitbank: 23 → 7、19 → 1、51 → 12 件。GMO XRP_JPY: 15 → 8 件)。
  sol_jpy だけは配信でも全部が (c) です。板が薄く、約定が無いまま最良気配が 3 bps 以上飛ぶことが 25 分で 67 回ありました。
- **GMO は配信のほうが 5 秒後の取り分が良く出ました** (3 銘柄とも)。ポーリングでは、向きの分からない約定を「届いた側」に当てていたぶんと、
  古い指値が残る時間が長いぶんが悪く出ていたと見られます。
- **bitbank の主要な銘柄は、配信でも約定が数件しかありません。** 幅 3 bps は刻み 40 個ぶん外側で、そこまで届く約定がほとんど無いからです。
  5 秒後の −4〜−5 bps は 2〜10 件の平均で、まだ何も言えません。
- **25 分・数件〜30 件の約定なので、どの数字も当てになりません。** 分かったのは「取り方で結果が変わる」ことと、変わる向きだけです。
  数字を信用できるものにするには、配信で数日ぶん記録する必要があります。
- 配信で組み立てた板は、同じ時刻のポーリングの板と最良気配が 97〜100% 一致しました (前後 2 件までのずれを含む。sol_jpy だけ 90%)。
  約定は、件数も代金も 6 銘柄すべてで完全に一致しました。

## 集計 (`report`)

銘柄ごとに、スプレッド (bps) の中央値・p25・p75、最良気配の厚さ (ドル)、約定の件数/時と代金/時、
取りこぼしの回数、ポーリングの遅延を出します。

「片側スプレッド − メイカー手数料」は、最良気配に並んで約定し、**その後ミッドが動かなかった場合** の
1 回あたりの取り分の上限です。実際には約定の直後に値段が不利に動く (逆選択) ので、これだけで判断せず
`replay` を見てください。

期間は `--hours N` (記録の末尾から遡る) か `--since` / `--until` (書き方は下の「長い記録を読む」) で切れます。
`report` / `replay` / `paper-report` は db を **読み取り専用** で開きます。記録中の db に向けても何も書かず、
記録側の書き込みも待たせません (読み取りは 2000 件ずつの短い問い合わせに切っています)。無いファイルを指すと、作らずにエラーで止まります。

## 再生 (`replay`)

記録を時刻順に流し、クォーターが出した指値に、記録にある約定のうちどれが当たったかを決めます。
本当に指値を出したわけではないので、当たったかどうかは **仮定** です。実際より良く見えない側に倒しています。

### 時間の扱い (先読みしない)

- 気配 k を見てクォーターが値段を決めます。使えるのは気配 k 以前の気配と約定 (直近の履歴)、今の在庫、
  クォーターが自分で持つ `state` だけです (下の「クォーターの書き方」)。
- 決めた指値が板に載るのは `--latency-ms` 後 (既定 250ms)。それまでは前の指値が残ります。
- 取引所の時刻が気配 k+1 以前の約定は、気配 k+1 より先に、その時点で板に載っている指値に当てます。
  ポーリングの間隔より細かい前後関係は分からないので、約定の時刻だけを信じます。

### 約定の仮定 (買い指値 p の場合。売りは逆)

- **(a) 値段を抜けた**: 売り手主導の約定が p より安く出たら約定。ただし数量はその約定の数量まで
  (記録にある売りの量より多くは買えません)。
- **(b) 列を消化して**: p ちょうどの売り手主導の約定は、まず自分より前の列を消化し、残りがあればその分だけ約定。
  列は、指値を決めたときの気配で p に並んでいた数量です。減るのは記録にある約定でだけで、前の人の取消では
  減らしません。p が最良気配より内側なら列は 0。記録した段数より外側なら列が分からないので (a) でしか約定しません。
- **(c) 気配が抜けていた**: 次の気配で最良売りが p 以下になっていたら、残りはすべて p で約定したとみなします。
  約定の記録に抜けがあっても、値段が指値を抜けたのに「約定しなかった」ことにしないためです。
  **これはかなり不利な側の仮定です。** 中位の銘柄では、約定が 1 件も無いまま気配全体が数 bps 動くことが
  よくあります (他のメイカーが値段を出し直すだけ)。実際にはその全部で古い指値が拾われるわけではありません。
  気配の間隔が粗いほど (c) が増えて結果を支配します (下の「実データで分かったこと」)。
  `--no-cross-fill` で外せます。外した結果は甘い側なので、**2 つの間に実際がある** と読んでください。
- 値段が同じなら指値は置いたままで列の位置を保ち、値段が変わったら取り消して出し直し、**列の最後尾** に並びます。
- 相手の気配に当たる値段 (買い ≥ 最良売り) は出しません (ポストオンリーで弾かれる扱い)。
- 気配が 60 秒以上途切れたら記録の切れ目とみなし、指値をいったんすべて取り下げます。
- 同じ時刻の約定は、1 本の成行が板を食い進む順 (売り手主導なら高い値段から) に流します。

### 出力の読み方

- **約定の内訳 (a)/(b)/(c)**: 種類ごとの件数・代金・約定した瞬間の取り分。(c) が大半なら、その結果は
  データではなく仮定 (c) と気配の間隔で決まっています。`--no-cross-fill` と並べて幅を見てください。
- **(a)+(b) の、市場の約定代金に対する割合**: 高すぎる (数十 % など) ときは仮定を疑ってください。
  スプレッドの内側に出す設定では「前に誰もいない」扱いになるので高く出ます (限界の 2 と 3)。
- **損益の内訳**: スプレッドの取り分 (約定の直前のミッド − 約定値段) + 手数料 + 在庫の評価損益 = 合計。
  合計は現金の出入りから別に計算していて、「内訳の和との差」は 0 になるはずです。
  **ファンディングは未計上** です。残った在庫は最後のミッドで評価していて、閉じる費用は入っていません。
- **逆選択**: 約定した瞬間の取り分と、N 秒後のミッドで測り直した取り分。差が逆選択です。
  N 秒後は「N 秒たった後の最初の気配」で測るので、気配の間隔より細かくは測れません。
- **在庫**: 最大、時間平均、最後に残った分。

### 長い記録を読む (期間・日ごと・± ・複数銘柄・現物の在庫)

どれも付けたときだけ効きます。付けなければ出力は今までと同じです。`replay --run` (paper との突き合わせ) とは一緒に使えません。

```bash
python -m tbf.mm replay --db gmo.sqlite --coin BTC_JPY --since +24h --until +48h     # 記録の先頭から 24〜48 時間
python -m tbf.mm replay --db gmo.sqlite --coin BTC_JPY --since 2026-11-25T03:00 --until 2026-11-26T03:00   # UTC
python -m tbf.mm replay --db gmo.sqlite --coin BTC_JPY --by-day --se                 # 1 週間を通しで流し、日ごとに割る
python -m tbf.mm replay --db gmo.sqlite --by-day                                     # 全銘柄。銘柄ごとの 1 行と合計
python -m tbf.mm replay --db bitbank.sqlite --coin xrp_jpy,eth_jpy --spot-inventory  # 現物: 持っていない分は売らない
python -m tbf.mm report --db gmo.sqlite --since +24h --until +48h
```

- **期間 (`--since` / `--until`)**: `2026-11-25T03:00` は **UTC** (`2026-11-25T12:00+09:00` のように時差を付ければその時刻)。
  `+24h` (`d` / `h` / `m`) は **その db の最初の気配から** の時間。`--since` は含み、`--until` は含みません
  (`+0h〜+24h` と `+24h〜+48h` は重ならない)。`--hours` (末尾から遡る) とは一緒に使えません。
  区間の頭では **在庫 0・履歴なし** から始めます (前の区間の在庫は引き継ぎません)。
- **区間の終わりと「N 秒後」**: 指値を出すのは `--until` まで。5 秒後・60 秒後の取り分は、**区間より後の気配も使って測ります**。
  測るだけでクォーターには渡さない (先読みにならない) ことと、使わないと区間の終わり 60 秒の約定が毎回落ちて、
  区間を足しても通しと合わなくなるためです。`paper-report` / `replay --run` と同じ扱いです。
- **日ごとの表 (`--by-day`、`--by-hours N`)**: 1 回の再生の約定を、**UTC** の日 (または N 時間) ごとに割り、
  約定の件数・買/売・代金・瞬間 / N 秒後の取り分 (`--horizons` の秒数) を並べます。`--jst` で区切りを日本時間にします
  (`--since` / `--until` は UTC のまま)。**在庫は通し** で、列はその区切りの終わりに持っていた枚数です。日ごとに在庫を 0 に戻したいときは、
  `--since` / `--until` で 1 日ずつ流してください。
- **取り分の ± (`--se [分]`)**: 標準誤差です。取り分は代金で加重した平均 (Σ取り分の金額 / Σ約定代金) なので、約定を時間の塊
  (既定 5 分) に分け、塊ごとの金額 N と代金 D から `sqrt(G/(G−1)·Σ(N − R·D)²) / ΣD` (R は全体の取り分、G は約定のあった塊の数) で出します。
  続けて付いた約定は同じ値動きに乗っていて独立でないので、件数ではなく塊で数えます。塊が 2 個に満たなければ `?`。
  **± の 2 倍より 0 に近い取り分は、0 と区別できていない** と読んでください。塊が 10〜20 個しか無いうちは ± 自体も当てになりません。
  日ごとの表と銘柄ごとの表には、`--se` を付けなくても ± が付きます。
- **複数の銘柄**: `--coin` を省く (その db の全銘柄) か、カンマ区切りで渡すと、最初に銘柄ごとの 1 行と合計の表が出て、
  その下に銘柄ごとの内訳が続きます。合計の取り分は全銘柄の約定を合わせて代金で加重したもの。金額はそのまま足しています
  (1 つの db は 1 つの会場なので建値の通貨は同じ)。銘柄は 1 つずつ順に流し、互いの在庫は見ません。`--coin` に 1 つだけ渡せば今までどおりです。
- **現物の在庫制約 (`--spot-inventory`)**: 現物の銘柄 (bitbank、GMO の現物。記録にある銘柄の情報で判断) で、売り指値の数量を
  **板に載せる時点で持っている在庫まで** に絞ります。在庫が最小数量に届かなければ売り指値は出しません。在庫 0 から始まるので、
  買いが約定するまでは買い指値だけです。売りから入れる銘柄 (GMO のレバレッジ、Hyperliquid) には効きません。
  値段が同じで置いたままの売り指値は、後で在庫が増えても数量を増やしません (列の位置を保つ今までの扱いと同じ)。
  **既定は付けない (今までどおり、在庫 0 から売れてしまう甘い側)** です。既存の結果と `paper` / `replay --run` の突き合わせを変えないためで、
  現物の銘柄を評価するときは付けてください。付けないときは、今までどおり末尾に「在庫を 0 より下に押し下げた売り」の件数が出ます。
- **大きい記録**: 気配と約定は 2000 件ずつ読み、メモリに残すのは約定の一覧だけです。2 時間の記録を 84 倍に並べた db
  (0.9GB、1 銘柄の気配 110 万件) で、`replay` は 1 銘柄 24 秒・37MB、3 銘柄と合計で 68 秒・65MB、`report` は 10 秒・約 210MB でした
  (手元の計測。変更前は同じ db で `replay` 2.2GB、`report` 3.8GB)。`paper-report` と `replay --run` は今も区間の気配を全部メモリに載せます。

### クォーターの書き方

クォーターは「気配と約定の履歴、自分の在庫を見て、どこに指値を出すか」を返す関数です。
`tbf/mm/quoter.py` に書いて `QUOTERS` に足し、`--quoter 名前` で選びます (`replay` でも `paper` でも同じ)。

```python
from tbf.mm.quoter import QUOTERS, Context, Quote

def my_quoter(ctx: Context) -> Quote:
    mid = ctx.book.mid
    ...
    return Quote(bid=..., bid_size=..., ask=..., ask_size=...)   # None の側は出さない。数量は枚数

QUOTERS["my_quoter"] = (my_quoter, {"half_spread_bps": 3.0})    # 名前 -> (関数, パラメータの既定値)
```

再生でも paper でも、同じ `Sim` が同じ `Context` を組み立てて呼びます。呼ばれるのは気配が 1 つ進むたびです
(前に決めた指値がまだ板に載っていない間は呼ばれません)。

| 渡るもの | 意味 |
|---|---|
| `ctx.now` | 判断の時刻 (取引所の時刻、ms)。今の気配の時刻と同じ |
| `ctx.book` | 今の気配。`bids` は高い順、`asks` は安い順の `(値段, 数量)`。記録した上位の段 (既定 10 段) が入っている。`best_bid` / `best_ask` / `mid` / `spread_bps` もある |
| `ctx.inventory` | 今の在庫 (枚数。売り越しは負)。`now` までの約定で決まった分 |
| `ctx.params` | パラメータ (既定値に `--param` を重ねたもの)。数値だけ |
| `ctx.books` | 気配の履歴。古い順で、最後が今の気配。直近 600 秒ぶん |
| `ctx.trades` | 市場の約定の履歴 (`time` / `side` / `px` / `sz`)。古い順。時刻が `now` 以前で、直近 600 秒ぶん。`side` は仕掛けた側 (`B` = 買い手主導、`A` = 売り手主導)。自分の疑似約定は入っていない |
| `ctx.state` | この銘柄・この実行だけの dict。最初は空。指数移動平均など、次の呼び出しまで持ちたい値を入れる |

- **先読みはできません。** 履歴に入るのは `now` 以前のものだけで、それより後の気配・約定は次の呼び出しで初めて見えます。
  約定は時刻が `now` ちょうどのものまで入ります (実際の bot には届くのに少し時間がかかるので、直前の数百 ms の約定に
  頼る作りは実際より良く見えます)。
- **履歴には上限があります** (600 秒、かつ気配・約定それぞれ 5000 件。`quoter.py` の `HISTORY_SEC` / `MAX_HISTORY`)。
  それより長い記憶が要るなら `state` に自分で畳み込みます。
- **実行の最初は履歴が短い** (1 件から始まります)。足りないときの扱い (出さない、など) は自分で決めます。

守ること (破ると、再生と paper の結果が合わなくなるか、成績が嘘になります):

- 同じ `Context` には同じ `Quote` を返す。今の時計 (`time.time`)、乱数、ファイルやネットワークを使わない。
- 覚えておきたい値は `ctx.state` に入れる。モジュールの変数やクロージャに持たない (銘柄をまたいで混ざり、再生をやり直すたびに結果が変わる)。
- `ctx.book` / `ctx.books` / `ctx.trades` / `ctx.params` を書き換えない。
- 履歴が連続していると決めつけない。記録の切れ目や約定の取りこぼしがあるので、時刻の差を見る。約定の件数や代金は下限。
- `state` は実行をまたがない。paper を起動し直すと空から始まる (指数移動平均などは温まるまで時間がかかる)。
- 標準ライブラリと `tbf` だけを使う。

テストでは `Context.of(book, inventory, params)` で気配 1 枚から `Context` を作れます。履歴を使うクォーターは、
`simulate(books, trades, my_quoter, params, sz_decimals=...)` に合成データを流して確かめます (`tests/test_mm.py` の `history_quoter` が例)。

刻みへの丸め (買いは切り下げ、売りは切り上げ)、数量の丸め、ポストオンリーの判定は再生側がやります。
基準は `baseline` です:

| `baseline` のパラメータ | 既定 | 意味 |
|---|---|---|
| `half_spread_bps` | 3 | ミッドから片側に離す幅 |
| `size_usd` | 100 | 片側 1 本の大きさ |
| `max_inventory_usd` | 500 | 在庫がこれ以上になったら、増やす側は出さない |
| `skew_bps` | 3 | 在庫が上限のとき、両方の値段を在庫を減らす向きにずらす幅 (在庫に比例) |

既定値は出発点で、採用の判断に使った値ではありません。

### 改善案のクォーター (候補。採否は決まっていません)

どれも在庫の扱いは `baseline` と同じで (上の 4 つのパラメータもそのまま使います)、変えるのは 1 つずつです。
既定値は出発点で、採用の判断に使った値ではありません。

| 名前 | 何を変えるか | 足したパラメータ (既定) |
|---|---|---|
| `vol_spread` | **荒さで幅を変える。** 幅 = max(`half_spread_bps`, `vol_mult` × 直近の実現ボラ)。実現ボラが `vol_pause_bps` を超えたら、在庫を増やす側は出さない (減らす側は残す) | `vol_window_sec` (60) 荒さを測る窓、`vol_mult` (1) 0 なら広げない、`vol_pause_bps` (6) 0 以下なら止めない |
| `lean` | **真ん中をずらす。** ミッドから `imb_bps` × 板の偏り + `flow_bps` × 約定の偏り だけ動かす (買いが厚い・買い手主導が多いなら上へ)。ずれが `one_side_bps` 以上なら、踏まれる側 (上がりそうなら売り) は出さない | `imb_bps` (1)、`flow_bps` (0.5)、`one_side_bps` (1) 0 以下なら両側とも出す |
| `vol_lean` | 上の 2 つを合わせたもの (幅は荒さで、真ん中は偏りで) | 上の 6 つ。独自のものは無い |
| `cooldown` | **約定した側をしばらく休む。** 買いが約定したら `cooldown_sec` 秒は買いを出さない (売りも同じ) | `cooldown_sec` (10) |

言葉の中身 (`tbf/mm/quoter.py` の定数。パラメータではなく決め打ち):

- **実現ボラ**: 窓の中の気配どうしのミッドの動きの 2 乗和を経過時間で割り、「5 秒のあいだに動く幅 (1σ、bps)」に直したもの。
  記録した 3 銘柄では中央値が 3 bps 前後、上位 1 割が 4.5 bps 前後でした。15 秒を超える気配の空きは切れ目とみなし、それより前は使いません。
- **板の偏り**: 最良気配 1 段の (買いの数量 − 売りの数量) / 合計。−1〜+1。
- **約定の偏り**: 直近 60 秒の (買い手主導 − 売り手主導) / 合計 (代金)。−1〜+1。**直前 500ms の約定は使いません**
  (履歴には `now` ちょうどの約定まで入るので、そのまま使うと実際より良く見えるため)。約定が無ければ 0。

履歴が足りない間:

- `vol_spread` / `vol_lean` は、気配が窓の半分 (既定で 30 秒) 続くまで **出しません**。実行の最初と、記録の切れ目の直後がそうです。
- `lean` は最初から出します。約定の履歴が無い間は板の偏りだけで動きます。
- `cooldown` は履歴を使いません。約定は、前に呼ばれたときからの在庫の変化で知ります (`state`)。

気をつけること:

- `lean` の約定の偏りは、paper では気配より後に届いた約定も「その気配の時点で見えていた」扱いになります
  (paper は約定のポーリングを待ってから気配を処理するため)。REST で 10 秒おきに約定を取る実際の bot には、
  500ms の遅れでは届きません。**約定の偏りが効いて見えたら、まずこれを疑ってください。**
- 板の偏りを 1 段にしたのは、前半の記録 (27 分) で 1 / 3 / 5 / 10 段を比べた結果です。合わせ込みの余地がある値です。
- **一次評価 (2026-11-22) では、どの案も `baseline` との差が誤差の中でした。** 前半 27 分で値を選び、後半 76 分
  (INJ / MON / ZRO) で見て、5 秒後の取り分は `baseline` −3.65 / −2.99 bps ((c) あり / なし) に対し、各案は
  −3.6〜−4.0 / −2.3〜−3.3 bps (標準誤差の目安は 0.4 / 0.9 bps)。後半でも向きが保たれたのは板の偏り (1 段) だけで、
  約定の偏りは向きが逆になりました。採否を言うには数日ぶんの記録が要ります。
- 幅を広げる案は、約定が減るぶんだけ 1 件あたりの取り分が良く見えます。比べる相手は `baseline` の既定ではなく、
  同じくらい約定が減るように `half_spread_bps` を広げた `baseline` です。

## 実況の paper (`paper` / `paper-report`)

`record` と同じポーリングで気配と約定を **記録しながら**、同じクォーターをその場で動かし、疑似的に約定を付けます。
発注はしません。鍵も要りません。記録は `record` と同じテーブルに同じ形で残るので、あとで `replay` にそのまま使えます。

```bash
python -m tbf.mm paper --coins MON,INJ --param half_spread_bps=4
python -m tbf.mm paper-report                 # 最後の run
python -m tbf.mm paper-report --run 3 --hours 24
```

**`paper` は記録を兼ねます。別に `record` を回さないでください。** 同じ IP で両方回すと流量制限の重みが倍になります
(起動時の歯止めは 1 つのプロセスの分しか数えません)。

### 再生と同じコードで約定を付ける

約定の判定は `replay` と同じ `Sim` (`tbf/mm/replay.py`) だけを通ります。仮定 (a)(b)(c)、板に載るまでの遅れ、
ポストオンリーなどはすべて上の「再生」のとおりです。**paper が貯めた記録を後から流し直すと、同じ結果になります。**
突き合わせるコマンドがあります:

```bash
python -m tbf.mm replay --run 3     # run 3 と同じ設定・同じ区間を再生し、末尾に「paper run 3 との突き合わせ: 一致」と出す
```

これを成り立たせるために、気配は受け取ってすぐには処理しません。約定のポーリングは気配より間隔が長く、
気配を受け取った時点では、それ以前の約定がまだ全部は届いていないからです。気配は、**それを受け取った後に
始めた約定のポーリングが成功してから** 処理します。成績は実際の時計より最大で約定の間隔 (既定 10 秒) ぶん遅れて
付きますが、クォーターが見るのはその気配と、その時点までの約定で決まる在庫だけで、再生と同じです。
止めたときに未処理だった最後の数件の気配は、その run の成績に入りません (記録には残ります)。

### 再生と食い違いうる点

食い違いうる出来事は回数を数えて `paper-report` の「食い違い」の列に出します。0 なら `replay --run` と一致するはずです。

- **遅れた約定**: 処理済みの気配より前の時刻の約定が、後から届いた。paper はもう通り過ぎているので使えませんが、
  再生は記録に残った時刻どおりに使います。
- **遅れた気配**: 処理済みの気配より前の時刻の気配が、後から届いた。

ほかに食い違う場合:

- run の後で、その区間の記録を足したり消したりしたとき。
- コード (`Sim` やクォーター) を run の後で変えたとき。`replay --run` は今のコードで流し直します。run に残るのは
  クォーターの名前とパラメータだけで、コードの版は残していません。
- クォーターが落ちたとき。その銘柄の paper はそこで止め (ログに出ます)、記録は続けます。再生は最後まで流そうとして同じ所で落ちます。

逆選択の「N 秒後」は、どちらも記録から後で引いています (区間より後の気配も使う)。

### 再起動すると新しい run

止めて起動し直すと **新しい run として在庫 0 から** 始まります。前の run の在庫や損益は引き継ぎません (起動時のログにも出ます)。
記録 (気配・約定) は同じ sqlite の続きに足されます。パラメータを変えた実行が混ざらないよう、成績はすべて run の id で分かれていて、
`paper-report` は run どうしを足しません。落ちて systemd が起動し直した場合も新しい run になるので、
長く回した成績を見るときは run が切れていないかを先に確かめてください。

### 残るもの

| テーブル | 中身 |
|---|---|
| `paper_runs` | run ごとの設定: 開始・停止の時刻、銘柄、クォーター名、パラメータ、手数料、遅れ、仮定 (c) の有無、ポーリングの間隔 |
| `paper_fills` | 疑似約定: 時刻、銘柄、向き (1 = 買い、-1 = 売り)、値段、数量、種類 (`through` = (a)、`queue` = (b)、`cross` = (c))、手数料、直前のミッド |
| `paper_account` | 口座のスナップショット (1 分に 1 行): 在庫、現金、手数料、ミッド、評価損益、食い違いの回数、成績の内訳 (JSON) |

### `paper-report` の読み方

- 最初の表が銘柄ごとの 1 行と合計。その下に、`replay` と同じ形の銘柄ごとの内訳が続きます。
- **日ごと・時間帯ごと (UTC の時) の損益** は、口座の評価額の差です。持っている在庫の値動きを含みます。
  1 分ごとのスナップショットから出しているので、時間の境目は最大 1 分ずれます。
- `--hours N` は run の末尾から N 時間ぶん。始点で持っていた在庫は、始点のミッドで買ったものとして数え直します。
- ファンディングと、残った在庫を閉じる費用は入っていません。

### 日次のまとめ

環境変数 `WEBHOOK_URL` (Discord / Slack 互換) があれば、起動時に 1 回と、以後 24 時間ごとに直近 24 時間のまとめを送ります。
未設定なら何も送りません。

### サーバーへの設置 (人間がやる)

`deploy/mm-paper.service` が systemd の unit の雛形です (`deploy/arb-shadow.service` と同じサンドボックス)。
`deploy/setup-server.sh` は mm を設置しません。arb を設置済みのサーバー (コードが `/opt/trade-bot-factory` にある) なら:

```bash
sudo useradd --system --no-create-home --shell /usr/sbin/nologin mm
sudo install -d -m 0700 -o root -g root /etc/mm
sudo tee /etc/mm/env >/dev/null <<'ENV'
MM_COINS=MON,INJ
# MM_ARGS=--param half_spread_bps=4
# WEBHOOK_URL=https://discord.com/api/webhooks/...
ENV
sudo chmod 0600 /etc/mm/env
sudo install -m 0644 /opt/trade-bot-factory/deploy/mm-paper.service /etc/systemd/system/mm-paper.service
sudo systemctl daemon-reload && sudo systemctl enable --now mm-paper
journalctl -u mm-paper -f
sudo -u mm python3 -m tbf.mm paper-report --db /var/lib/mm/mm.sqlite     # /opt/trade-bot-factory で実行
```

- 記録は `/var/lib/mm/mm.sqlite` (1 銘柄・2 秒間隔で 1 日 25MB ほど増えます。消す仕組みはありません)。
- `MM_COINS` や `MM_ARGS` を変えたら `sudo systemctl restart mm-paper`。新しい run になります。
- 既定の間隔なら 3 銘柄までです (流量制限の歯止め)。arb と同じサーバーで回しても、Hyperliquid を叩くのは mm だけなので重みは変わりません。
- この雛形は実際の systemd では試していません。

### 国内 2 社の配信を記録し続ける (人間がやる)

GMO コインと bitbank の配信 (WebSocket) を、会場ごとに 1 プロセスで記録し続けます。paper は回しません
(記録さえあれば、どのクォーターでも後から `replay` で試せるので)。発注はせず、鍵も要りません。

1. VPS を作成 (Ubuntu 24.04、1 vCPU / 1GB、ディスク 20GB 以上。**東京リージョン**)。**作成時に SSH 公開鍵を登録**する
2. SSH でログインして実行 (`<ブランチ>` は `tbf/mm/streams.py` が入っているブランチ。main に入るまでは作業ブランチ名):
   ```bash
   git clone --branch <ブランチ> https://github.com/sollall/trade-bot-factory.git /tmp/tbf
   sudo BRANCH=<ブランチ> bash /tmp/tbf/deploy/setup-mm-record.sh
   ```

スクリプトがやること: `deploy/setup-server.sh` と同じ守り (自動セキュリティ更新、SSH の鍵認証のみ化、ファイアウォール、fail2ban)、
ログイン不可の専用ユーザー `mm`、コードは root 所有、両会場に 1 分ずつ試しにつないで集計を表示、
`deploy/mm-record@.service` を `mm-record@gmo` / `mm-record@bitbank` として常駐。

- 記録は `/var/lib/mm/gmo.sqlite` と `/var/lib/mm/bitbank.sqlite`。既定の 3 銘柄ずつで、2 時間に 11MB / 15MB ほど
  (合わせて 1 日 0.3GB、1 週間 2GB 強)。消す仕組みはありません。`df -h /var/lib/mm` で残りを見ます。
- 銘柄は `/etc/mm/gmo.env` / `/etc/mm/bitbank.env` の `MM_COINS`。変えたら `sudo systemctl restart mm-record@<会場>`。
- 途中経過: `cd /opt/trade-bot-factory && sudo -u mm python3 -m tbf.mm report --venue gmo --db /var/lib/mm/gmo.sqlite --hours 24`。
  「配信の切断」と「約定の取りこぼしの可能性」の回数、「配信の遅れ」をここで見ます。
- 再生も VPS の上でできます (標準ライブラリだけ): `sudo -u mm python3 -m tbf.mm replay --venue gmo --db /var/lib/mm/gmo.sqlite --coin BTC_JPY`。
- 止める: `sudo systemctl disable --now mm-record@gmo mm-record@bitbank`。
- **自動の更新**: 1 分ごとに、VPS が自分で GitHub のブランチを見に行き、進んでいれば取り込みます
  (`deploy/mm-update.sh` を `mm-update.timer` が動かす)。GitHub に VPS の鍵は預けません。
  - 記録を起動し直すのは、記録に関係するファイルが変わったときだけ (数秒の切れ目)。再生・集計・クォーターだけの変更では止めません。
  - 取り込んだ版が読み込めない、起動し直した記録が動かない、のどちらかなら前の版に戻します。ブランチが巻き戻されていたら取り込みません。
  - 更新スクリプト自身と unit は取り込みません (root で動くものを、push だけで書き換えられないように)。
    変わったときはログに出るので、設置スクリプトを流し直します。
  - 追いかけるブランチは `/etc/mm-update.env` の `BRANCH`。今すぐ動かす: `sudo systemctl start mm-update`、
    結果: `journalctl -u mm-update -n 20`、やめる: `sudo systemctl disable --now mm-update.timer`。
  - **ブランチに push できる人は、VPS の上で (権限を絞った `mm` ユーザーとして) コードを動かせます。** 今は鍵を置かない記録専用なので
    それで済みますが、発注の鍵を置く本番では、追いかけるのは main だけにし、手仕舞いの手順とセットで作り直します。
- スクリプトは構文チェック、unit は `systemd-analyze verify` までで、実機では試していません。
  プロキシを通さない直接の WebSocket 接続も未確認です (スクリプトの「1 分だけ試しに記録」で最初に分かります)。

## 確かめたこと・確かめていないこと

確かめたこと (2026-11-22、手元から公開 API で):

- `l2Book` は片側 20 段、`recentTrades` は 10 件で並び順は一定しない。
- メイカー手数料の既定 +0.015% は、`{"type":"userFees"}` が返す料率表の基本ティア (`add = 0.00015`) と一致。
  テイカーは 0.045% (`cross = 0.00045`) で `DEFAULT_FEES` と同じ。
- 値段の刻みの規則 (有効 5 桁、小数は 6 − szDecimals 桁まで) に、記録した気配と約定の値段がすべて収まる
  (INJ / MON / ZRO、15 分 + 12 分の 2 回の記録で約 4.7 万個の値段。外れは 0)。
- 約定の `side` の向き: `B` はその直前のミッド以上、`A` は以下で成立している (305 件中 298 件。
  残りは気配と約定の間に値段が動いたぶんと見られる)。
- 毎分の重みが計算上 570〜600 の設定で計 27 分回して、429 は 0 回。これは「この量では止められなかった」
  というだけで、重みの値が正しいことの確認ではない。

- 実況の paper を 3 銘柄で 4 分 (SIGTERM で停止) + 11 分回し、どちらの run も `replay --run` と約定・損益が一致。
  遅れた約定・遅れた気配は 0 回。止めた後の sqlite は `PRAGMA integrity_check` が ok。

- 国内 2 社 (2026-11-22、手元から公開 API で。GMO は 5 銘柄・bitbank は 4 銘柄を 20 分ずつ記録):
  応答の形 (上の表)、手数料・刻み・最小数量が API から取れること、記録した気配と約定の値段がすべて刻みの倍数であること、
  bitbank の約定の向き (直前・直後の気配と突き合わせて、整合 65 件・逆 0 件・判定できず 39 件)、
  GMO の約定が 2 行で 1 件になっていること、実況の paper が両社で `replay --run` と一致すること (4 分ずつ)。
- Hyperliquid の既存の記録 (`data/mm.sqlite`) の `report` / `replay` / `paper-report` の出力は、会場対応の前後で一字も変わらない。

確かめていないこと:

- 国内 2 社の公開 API の流量制限の上限 (どちらも公式に記載が無い。GMO は実測で約定の取得がときどき弾かれる)。
- GMO の気配の時刻 (`responsetime` で代用) と約定の時刻が同じ時計か。GMO の約定で BUY と SELL が対になる理由。
- 国内の会場での指値の遅れ (250ms のまま)、発注側の決まり (ポストオンリーの扱い、最小数量が発注でも同じか)。
- 会場対応の後、Hyperliquid に実際にポーリングしての記録 (別の記録が動いていたので、フェイクのテストと既存の記録の再生だけ)。
- paper を長時間回したときに「遅れた約定」がどれだけ出るか (15 分で 0 回、というだけ)。
- 日次のまとめの Webhook 送信 (24 時間後に初めて動くので、実際には一度も走らせていない) と、`deploy/mm-paper.service` の実機での動作。

- 流量制限の重みと上限 (上記)。
- 手数料・刻み・最小注文額 (10 ドルと仮定) の公式ドキュメントでの裏取り。割引 (出来高・ステーキング・紹介) は未考慮。
- 指値が板に載るまでの遅れ (250ms は info の往復から置いた仮定。発注の経路では測っていない)。
- 気配の `time` と約定の `time` が同じ時計か。同じ取引所の時刻として扱っているが、気配の `time` は
  手元で投げた時刻より 0.3 秒ほど前を指していて、気配が少し古い可能性がある。

## 実データで分かったこと (2026-11-22、INJ / MON / ZRO、27 分ぶん)

短すぎて損益の良し悪しは何も言えません。仕組みについて分かったことだけ書きます。

- **約定が無いまま気配が動く。** 3 秒の間にミッドが動く幅は中央値 0.85 bps、上位 1 割は 4 bps 以上 (INJ)。
  その多くは約定を伴いません。約定は 1 銘柄あたり毎時 170〜310 件しかありません。
- そのため 3 秒間隔の記録では、基準のクォーターの約定の 3〜8 割強 (件数) が仮定 (c) によるものでした。
  同じ記録の気配を間引いて間隔だけ変えると、(c) の件数は 1.5 秒 → 3 秒 → 6 秒で 10 → 13 → 20 件 (INJ) と増え、
  (a)+(b) は 8〜11 件でほぼ変わりません。**気配の間隔が粗いほど、結果は仮定 (c) で決まります。**
  これを受けて `--interval` の既定を 2 秒にしています。
- 最良気配の厚さは片側で中央値 80〜400 ドル、p25 は 100 ドルを切ることもあります。片側 100 ドルの指値でも
  「自分の指値が市場を変えない」前提 (限界の 3) はかなり怪しいです。
- 取りこぼしの可能性は 27 分で 5 回 (約定のポーリング 555 回中)。静かな時間帯の値です。

## 限界 (実際より良く見えうるところ)

1. **約定の記録が粗い。** REST では直近 10 件しか取れず、取りこぼした約定は列の消化にも (a) の約定にも
   使えません。値段が抜けた分は (c) で拾いますが、抜けずに戻った売買は見えません。
2. **列の前に割り込まれた分が見えない。** 気配を見てから指値が載るまでの間に同じ値段に入った注文は、
   実際には自分より前に並びますが、ここでは数えていません。とくに最良気配より内側に出した指値は
   「前に誰もいない」扱いです。
3. **自分の指値が市場を変えない前提。** 自分が内側に出せば他の参加者は出し方を変えますし、
   成行の出し手も変わります。小さい数量でしか成り立ちません。
4. **気配の間の動きが見えない。** 数秒の間に値段が往復しても、約定の記録が抜けていれば分かりません。
   逆に、気配が動いてすぐ取り消せた指値も、次のポーリングまで置きっぱなしの扱いです (これは不利な側)。
5. **残った在庫を閉じる費用とファンディングが入っていない。**
6. **記録の切れ目では指値を取り下げた扱い。** 実際に止まっていた間に不利に約定した分は入りません。
7. **取消・出し直しの回数に上限を置いていない。** 実際には発注側にも流量制限があります。

短い記録 (数十分) の損益は、ほぼその間の値動きと在庫の向きで決まります。クォーターの良し悪しを比べるには
数日ぶんの記録が要ります。

## 次の段階で要るもの

- **Hyperliquid の WebSocket での記録** (`l2Book` / `trades` の購読)。GMO コインと bitbank は対応済み (`tbf/mm/ws.py`)。
- **配信で数日ぶんの記録** (GMO コイン・bitbank)。25 分の記録では約定が数件〜30 件で、再生の数字はまだ当てになりません。
- 常時起動のサーバーで paper を数日回す (`deploy/mm-paper.service`)。
- 流量制限と手数料の公式の値での裏取り。
- ファンディングの計上 (`tbf/market/hyperliquid.py` の `fetch_funding` が使えます)。
- 複数銘柄を合わせた在庫とリスクの上限。
- 実際に発注する段階の前に: 鍵の扱い、発注・取消の経路と遅延の実測、止める手順。`docs/arb.md` の
  セキュリティのチェックリストと同じ水準が要ります。採否の判断は、独立した検証を通したうえで人間がします。
