# チェーン間アビトラ (シャドーモード)

複数チェーンの DEX で同じペアの価格を監視し、「チェーン A で売って、チェーン B で同量を買い戻す」と
手数料・ガス・リバランス費用を引いても利益が出る瞬間を記録します。**売買はしません。秘密鍵も不要です。**

目的は、実際にお金を入れる前に「自分のサーバーの速度で捕まえられる機会が、どれだけあるか」を測ることです。

## 仕組み

```
 毎 poll_interval_sec 秒
 ┌──────────────┐  JSON-RPC バッチ 1 回/チェーン
 │ arbitrum     │──┐  blockNumber, gasPrice,
 │ base         │──┼─ Uniswap V3 QuoterV2 で各サイズの
 │ optimism     │──┘  「売り (exact in)」「買い戻し (exact out)」見積もり
 └──────────────┘
        │
        ▼
 全ての (売るチェーン → 買うチェーン) × サイズ について
   純利益 = 売り代金 - 買い戻し代金 - ガス代(両側) - リバランス費用
        │
        ▼
 sqlite に記録: 機会 / 連続区間 (エピソード) / 1 分ごとの価格差 / RPC 遅延
```

- 両チェーンに在庫 (WETH と USDC) を持っておく前提です。ブリッジは偏りを戻すときだけで、その費用は `rebalance_bps` で按分します
- **エピソード**: 同じ向きの機会が何回のポーリングで連続したか。1 回しか観測されない機会は、実際には間に合わない可能性が高いので、
  `min_persist_polls` 回以上続いたものだけを「捕捉可能」として集計します
- 価格見積もりは Quoter (オンチェーンのシミュレーション) なので、プールの厚さによる価格影響も含まれます

## 使い方

```bash
python -m tbf.arb check                 # 設定がチェーン上の実態と合っているか (chain id / トークン / Quoter) を確認
python -m tbf.arb run                   # 監視開始 (Ctrl-C で停止)
python -m tbf.arb report --hours 24     # 集計
```

設定は `arb.toml`。チェーンやトークン、サイズ、閾値を変更できます。RPC は環境変数で上書きします:

```bash
export ARB_RPC_ARBITRUM=https://arb-mainnet.g.alchemy.com/v2/<key>
export WEBHOOK_URL=https://discord.com/api/webhooks/...   # 日次レポートの通知先 (任意)
```

既定の公開 RPC はレート制限が厳しく遅いので、数日以上回すなら Alchemy / Infura / QuickNode 等の無料枠のキーを使ってください
(1 チェーンあたり数秒に 1 回のバッチ呼び出しなので、間隔を 3〜5 秒にすれば無料枠に収まりやすいです)。

## サーバーへの設置 (月 5〜7 ドルの VPS)

1. VPS を作成 (Ubuntu 24.04, 1 vCPU / 1GB で十分)。**作成時に SSH 公開鍵を登録**する
2. SSH でログインして実行:
   ```bash
   git clone https://github.com/sollall/trade-bot-factory.git /tmp/tbf
   sudo bash /tmp/tbf/deploy/setup-server.sh
   ```
3. `/etc/arb/env` に RPC と Webhook を書いて `sudo systemctl restart arb-shadow`

スクリプトがやること: 自動セキュリティ更新、SSH の鍵認証のみ化、ファイアウォール (外からは SSH のみ)、fail2ban、
ログイン不可の専用ユーザー `arb`、コードは root 所有 (bot から書き換え不可)、systemd のサンドボックス
(`deploy/arb-shadow.service`)、起動前の設定チェック。

サーバーの場所は `report` の RPC 遅延 (p50/p95) を見て決めます。いくつかのリージョンで 1 日ずつ回して比べるのが確実です。

## 結果の読み方

- **価格差 (bps)**: 手数料 0.05% × 2 回 = 10bps を常に超えていないと利益は出ません。平均・最大でどの程度か
- **捕捉可能な回数と仮想利益**: 1 日あたりの仮想利益が、サーバー代・RPC 代・リスクに見合うか
- **RPC の遅延**: 遅延が大きいと、記録された機会の多くは実際には他の bot に先を越されます

仮想利益は「最初に観測した時点の純利益」で計算していますが、実際には
自分の取引による価格の変化・取引の失敗・先回りされる分で、これより小さくなると考えてください。

## 実際に売買する前に (セキュリティ)

シャドーモードで見込みがあると分かってから進める段階です。最低限これを満たしてから実装します:

**鍵**
- [ ] 秘密鍵をサーバーのファイルや環境変数に置かず、AWS KMS 等の「署名だけする」サービスを使う
- [ ] 取引用ウォレットは権限を絞ったスマートアカウント (Safe + 権限モジュール) にし、決めた DEX の決めた関数しか呼べないようにする
- [ ] 置く資金は失っても困らない額だけ。利益は定期的にハードウェアウォレットへ移す
- [ ] トークンの approve は必要額・信頼するコントラクトのみ。無制限 approve は残さない

**サーバーとアカウント**
- [ ] クラウド / GitHub / メールは二段階認証 (できればハードウェアキー)
- [ ] 依存パッケージは最小限、バージョンとハッシュを固定 (本リポジトリは標準ライブラリのみ)
- [ ] ログに鍵・秘密情報を出さない

**オンチェーン**
- [ ] トークンとプールは許可リスト制。流動性の下限を設ける (偽トークン・罠プール対策)
- [ ] スリッページ上限を厳しく。可能なら非公開の送信経路を使う (サンドイッチ対策)
- [ ] RPC は複数で突き合わせる
- [ ] ブリッジは実績のあるもの (USDC なら CCTP) だけ。ブリッジに置く額と時間を最小に

**運用**
- [ ] 1 分あたりの取引回数上限・1 日の損失上限・スマホから止められる停止スイッチ
- [ ] 全取引の記録 (日本ではスワップごとに課税対象)
